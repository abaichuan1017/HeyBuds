TRANSPORT AND SESSION FINDINGS

Addresses [block.function] below are decimal; explicit wire-byte sequences are
hexadecimal. Protocol facts are separate from HeyBuds integration requirements.

1. Service selection and model scope

- BMAP RFCOMM service UUID:
  00000000-deca-fade-deca-deafdecacaff
  Source A: python/pybmap/catalog.py; source C: RfcommTransport.kt.
- Standard SPP service UUID:
  00001101-0000-1000-8000-00805f9b34fb
  Source A's docs/quietcomfort-headphones-prince.md and qc_prince.py explicitly
  establish SPP SDP for prince (0x4075), with channel variation between units.
  This is NOT direct QC45 SDP evidence. qc45.py establishes historical channel
  8 and an initialization GET, but supplies no QC45 service-record capture.
  QC45 SPP is therefore a profile-scoped candidate, not a verified UUID-to-model
  mapping. A generic SPP UUID alone cannot identify Bose or a target model.
- Source A's macOS transport performs an SDP query but subsequently opens the
  configured channel directly; it does not extract a channel from the matching
  service record. Its connect helper probes fallback channels 2/8/9. Source D
  hardcodes channel 2. Neither behavior should be carried into HeyBuds.
- Source C reports that the BMAP UUID resolves to a non-control ff55 status
  beacon on its Android/Ultra Earbuds 2 setup. Its channel-2 reflection workaround
  is not a portable SDP fix. A matched UUID or an open socket does not establish
  BMAP. Require a complete, address-matched successful BMAP response; absent a
  usable normally discovered control service, leave that transport unavailable.
- qc45.py: duran, PID 0x4039, firmware report 4.0.4-4360+de6a887; RFCOMM init
  GET [0.1], wire 00 01 01 00, before other queries. This is a BMAP-version read,
  not an authentication key or a separate registration packet. Channel 8 is
  historical evidence only. There is no QC45 BLE validation in these snapshots.
- qc_ultra2.py: wolverine, PID 0x4082, firmware report 8.2.20+g34cf029;
  historical RFCOMM channel 2, no INIT_PACKET. A BLE implementation for generic
  QC Ultra headphones exists in source B, but does not establish gen-2 firmware
  coverage. The two generations must retain separate profiles.
- qc_ultra2_earbuds.py: edith, PID 0x4062. Source D reports macOS RFCOMM testing;
  source C reports actual Android LE control on firmware 8.4.8+gbb2cb60, including
  operation while another host owns audio. Those are upstream reports, not
  HeyBuds/macOS BLE verification.

2. GATT setup, security and registration

Use BMAP service 0000febe-0000-1000-8000-00805f9b34fb, with one selected
read/write/notify characteristic for commands AND responses:
  secure:   c65b8f2f-aee2-4c89-b758-bc4892d6f2d8
  unsecure: d417c028-9818-4354-99d1-2ac09d074591
  CCCD:     00002902-0000-1000-8000-00805f9b34fb
Sources B: docs/BMAP.md, ble/connection.rs; C: GattTransport.kt, PROTOCOL.md 15.

Source B's scanner.rs has 0000febe-0000-0000-0000-000000000000 instead of the
standard-base UUID above; its own BMAP document disagrees. Source C explicitly
identifies the zero-base app constant as dead code. Use the actual standard-base
service, not that scanner constant or a name substring as a service gate.

Select the secure characteristic first; validate its properties and enable
notifications before queries. Source C enables the CCCD with notification value
01 00 and waits for descriptor completion. CoreBluetooth integration should wait
for its notification-state completion rather than assume subscription succeeded.

On source C's tested earbuds, unencrypted BLE returns BMAP ERROR 20 (0x14,
InsecureTransport) for almost all useful reads, including [9.2]. The unsecure
characteristic answers [0.1], [0.2], and [4.14] in the reported pre-bond sweep.
A successful version GET therefore does not establish an encrypted usable control
session. The reported classic bond supplies LE encryption via CTKD on Android;
normal macOS pairing/CTKD behavior remains unverified. Selecting a characteristic
named secure is not itself evidence that the link is encrypted. Do not silently
fall back to unsecure to evade an encryption failure or copy the cloud/ECDH flow.

Source B writes WithoutResponse; source C uses WRITE_TYPE_DEFAULT (with response)
and waits for each write acknowledgement. The reported earbuds advertise both
properties. Treat write policy as transport configuration, honor the discovered
properties, and use the limit for the chosen write type. Neither upstream proves
both policies across QC45 and every Ultra generation.

GATT notification subscription and BMAP event registration are separate:
  SETGET [9.2]: [mode][4-byte big-endian block mask]
  mode 0=Overwrite, 1=Enable, 2=Disable; bit index is the function-block ID.
  Source C default blocks {1,2,4,5,31} -> mask 80 00 00 36.
  Bare BMAP request: 09 02 02 05 01 80 00 00 36
  Single-segment BLE value: 00 09 02 02 05 01 80 00 00 36
  GET [9.2]: 09 02 01 00; response is the active four-byte mask.
  [9.1] is NotificationReset, NOT a generic GetAll. Do not use it for discovery.
Sources C: BmapConnection.kt, Parsers.kt, PROTOCOL.md 10 and 15. Registration and
multi-frame drains were reported working over LE, but delivery of an actual
changed-value push over LE remains explicitly unobserved in GattTransport.kt.
Do not present successful registration as verified push delivery.

Source C reports idle LE disconnect at about 40 seconds, mitigated in its setup
by GET [0.1] every 20 seconds; immediate reconnect needs backoff (three attempts,
about 1.2 seconds apart). These are model/firmware observations, not universal
protocol timing guarantees. They justify session lifecycle policy and freshness
handling; no extra wire registration handshake is established by these sources.

3. BLE message boundaries and codec contract

Common BMAP frame:
  [fblock, function, flags, payloadLength, payload...]
  flags = (deviceID << 6) | (port << 4) | operator
  payloadLength is one byte; frame length is 4 + payloadLength (maximum 259).
  Operators: SET=0, GET=1, SETGET=2, STATUS=3, ERROR=4, START=5,
             RESULT=6, PROCESSING=7.
There is no added checksum, delimiter or second length field in the inspected
BMAP/BLE framing. The existence of an error named Chksum does not define one.
Sources A: protocol.py; B: bmap/packet.rs; C: Protocol.kt.

Each ATT characteristic value, in BOTH directions, is:
  [segmentHeader][BMAP message chunk]
  segmentHeader = ((segmentCount - 1) << 4) | zeroBasedSegmentIndex
  single segment = 00; two segments = 10,11; three = 20,21,22.
Strip exactly one header per value. Do not prepend another 00 to the BMAP body;
00 is already the single-segment header. Reassembled data can contain MULTIPLE
complete BMAP frames. Parse each by its length, not by notification count.
Sources B: bmap/segment.rs, ble/connection.rs, docs/BMAP.md;
C: BleFraming.kt, GattTransport.kt, BleFramingTest.kt, PROTOCOL.md 15.

Integration requirement for BoseGATTCodec.encode(Data, maximumWriteLength:):
maximumWriteLength is the characteristic VALUE limit, not ATT MTU. With value
limit W, chunk size is W - 1. In ATT-MTU notation M it is M - 4 (three ATT bytes
plus the segment header). At M=23, W=20, chunk=19; source C requests M=247 and
uses chunk=243 if granted. Source B fixes chunk=19. Do not subtract four from W,
or assume all incoming values are 20 bytes. Reject unusable W and messages needing
more than 16 chunks; a BMAP frame with payload >255 must already be rejected by
the BMAP encoder. Encode must preserve the full BMAP bytes without adding another
framing layer.

Integration requirement for feed(Data)->Data?: each call consumes one complete
notification value, not an arbitrary RFCOMM stream chunk. Return nil until a full
segmented message is available; returned Data is a BMAP buffer and may hold many
frames. reset must discard partial state on disconnect, timeout and errors.
Do not merge two messages after a lost tail or an index-zero restart. Validate
index <= last index, a stable last index and continuous segments; reject stray
tails, duplicate/missing segments and inconsistent headers. Bound buffered bytes
and partial-message lifetime. These strict validation requirements combine the
wire evidence with defensive integration policy; neither upstream reassembler
already supplies all of them (B accepts indexed storage; C does not check stable
last-index values). Do not treat source test presence as passing local tests.

Source C's report leaves multi-segment inbound notifications at MTU 23 unverified:
Android granted 247 even when 23 was requested. A successful single short response
or a synthetic fragmentation test does not close that hardware gap.

RFCOMM instead carries bare BMAP frames: retain incomplete frame tails across
callbacks and handle multiple frames per callback. Source D's callback-as-response
logic is not a safe message-boundary model. Serialize requests and separate push
STATUS from request completion; in source C, a START can be preceded by STATUS
before its RESULT. Match address and expected operator; ERROR and PROCESSING are
not completed settings. Preserve device/port fields for any routing validation.
Source A's prince reports PROCESSING before asynchronous state change, reinforcing
the need for profile-aware readback rather than a universal ACK success rule.

4. ProductInfo and safe capability queries

There is NO validated ProductInfo device-PID response address/layout in the four
fixed snapshots sufficient to implement a runtime model parser. Source A has
static DEVICE_INFO/catalog PIDs and OS discovery, not a ProductInfo PID decoder.
Source B's enums.rs declares PRODUCT_ID_VARIANT=0x05 and FIRMWARE_VERSION=0x04;
these conflict with executable source A profiles and source C BmapConnection.kt,
which consistently query firmware at [0.5] and decode a string. Source B does not
exercise those two constants in its initial queries. Do not infer PID from [0.5],
or invent a [0.3]/[0.6] layout because those IDs appear in a historical function map.

Established queries, with evidence limits:

  [0.1] GET  00 01 01 00
    BMAP version string. QC45 initialization; source C observed "1.2.0".
    It identifies protocol version, not product identity or link security.
  [0.2] GET  00 02 01 00
    All-function-block vector; source C observed 8f cc 23 ff.
    No validated generic decoder/bit-index mapping is supplied by these four.
    Do not assume it uses [9.2]'s block-ID mask ordering.
  [0.5] GET  00 05 01 00
    Firmware UTF-8 string in source A profiles/parsers and source C API/parser.
    Use as firmware evidence; do not reinterpret the bytes as a PID.
  [1.2] GET  01 02 01 00
    User-editable product name. Source C skips a leading flag byte, then reads
    UTF-8 and trims trailing NULs. It is not an immutable model identifier.
  [block.0] GET
    FblockInfo/version, e.g. [1.0] and [4.0] report "1.1.0" in A/C.
    Not an established generic list of implemented functions.
  [31.2] GET  1f 02 01 00
    AudioModes capabilities documented by B: byte 0 Bose-mode count, byte 1
    user-mode count, bytes 2-4 reserved, byte 5 flags (CNC, autoCNC, spatial,
    wind, user favorites, ANC toggle in bits 0-5), optional byte 6 minimum
    favorites. This is upstream documentation, not target-wide runtime proof.
  [31.8] GET  1f 08 01 00
    Source C: [slotCount, favoritesMaskHigh, favoritesMaskLow]. The big-endian
    mask selects starred indices. Validate fresh length/count and per-slot
    responses; slot count alone does not establish write support or model.
  [31.6] GET  1f 06 01 01 <slot>
    ModeConfig. Require the model-appropriate full STATUS length (QC45 47;
    Ultra gen2 48) and editability/configuration flags before enabling writes.
  [31.1] START  1f 01 05 00
    GetAll drains multiple state frames; source C observed eleven mode-config
    frames. GET is the wrong operator on the reported firmware. Do not use
    every block's function 1 as GetAll: [9.1] is the counterexample above.
  [1.5] GET  01 05 01 00
    Read CNC capability/state only; a successful read does not authorize SETGET.
  [31.10] GET  1f 0a 01 00
    Gen2 live audio settings: [cnc, autoCnc, spatial, wind, anc] in source C.
    qc45.py explicitly reports FuncNotSupp here; do not fall back to a gen2 write.
  [4.14] GET  04 0e 01 00
    Device-management feature bits in C: bit0 CTKD, bit1 carousel, bit2 barge-in.
    Useful for transport/routing features, not a general product/function ID.

No verified generic available-functions parser is established. Source A's NOTES
function map is a particular device's observed list; source C demonstrates both
omissions and unsupported entries when applied to earbuds. Error 4 means function
unsupported; error 5 means operator unsupported in context and must not always be
reported as authentication required (GET on GetAll is an explicit example).

Runtime identity evidence that is actually present:
- Source A catalog: Bose vendor 0x05a7, QC45 0x4039, Ultra Headphones 2 0x4082,
  Ultra Earbuds 2 0x4062. macOS discovery uses IOBluetoothDevice.productID();
  Linux uses Bluetooth Modalias. Require associated vendor/service evidence
  and exact device association in HeyBuds. Do not import A's Linux fallback
  that assigns unknown BMAP devices the qc_ultra2 profile.
- Source C Advertisement.kt: Bose manufacturer company 0x009e; after the company
  bytes, require >=3 bytes and format byte 0. Product = 100 + (byte1 & 0x1f),
  variant = byte1 >> 5; flags are byte2. Reported prefix 00 a8 06 identifies
  edith as BLE product 108, variant 5. This is a different namespace from PID
  0x4062. No equivalent QC45/gen2-headphone advertisement mapping is established
  here. A product-class match does not bind a BLE peripheral to a particular
  classic paired device; same-name/same-model fallback is insufficient.
- Source C [4.5] GET with a six-byte peer address has a product layout when its
  isBoseProduct flag is set: payload [peerAddress(6), flags, PID_hi, PID_lo,
  variant, UTF-8 name...]. This describes a LISTED PEER, not necessarily the
  controlled headphones. It is not a replacement for missing own ProductInfo.

5. Configuration conflicts to preserve

- QC45 ModeConfig is 47-byte STATUS / 39-byte SETGET; Ultra gen2 uses 48/40.
  Source A qc45.py rejects the 40-byte QC45 write and lacks [31.10]. Never echo
  an entire STATUS as SETGET or silently default missing layout fields to zero.
- Source B's 48-byte ModeConfig document places wind at offset 46; source A's
  48-byte parser uses 45, whereas its 47-byte parser uses 46. Layout/firmware
  scope must remain explicit; this audit does not settle a universal offset.
- Earbud battery records are four bytes each with component ID at offset 3;
  invalid/absent levels such as ff remain unknown. A maps 1=right,2=left;
  C and D map 1=left,2=right. Available equal-level examples cannot resolve the
  direction. Preserve component IDs until asymmetric/single-ear evidence exists.
  A and C agree 3=case,4=aggregate. D incorrectly conflates 3 and 4 as case;
  do not carry that conflation into the implementation.
- Source C's multipoint bit0 versus A's older bit1 interpretation and button
  big-endian masks are additional model-sensitive differences. They must not
  be resolved by copying a whole headphones profile into earbuds.
- Full 47/48-byte config reads, fresh favorites counts, read-only [1.5], and
  gen2-only [31.10] are suitable independent capability gates. They do not
  replace identity evidence or establish a setting's success without readback.
