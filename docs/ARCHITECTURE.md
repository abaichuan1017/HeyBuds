# 实现说明

## 数据流

`IOBluetooth / CoreBluetooth → EarbudTransport → DeviceSession 品牌路由 → 各品牌编解码与状态归一化 → AppModel → SwiftUI`

OPPO 同时保留 RFCOMM 与 BLE GATT；新增品牌由 `BrandSession` 处理自己的线制，不调用 OPO 握手或封包。RFCOMM 只通过各品牌服务 UUID 的 SDP 记录获取通道；华为标准 SPP 只用于已识别型号，不凭通用串口服务判定品牌。OPPO BLE 只发现已知控制服务和写入／通知特征，先检索系统已连接外设，再定向扫描。传输间按序切换，同一会话不会同时打开两条链路。

## 生命周期与写入

- 设备会话将所有请求放入异步串行队列。响应按命令和序列匹配，避免超时旧响应确认新请求。
- RFCOMM 的 NSData 由传输持有直到异步写完成回调；按 MTU 分块。BLE 遵循特征写属性、最大长度及无响应写背压。
- 重连创建新会话，旧会话回调失效。断连清空实时状态，待处理请求收到取消结果。
- 界面展开时加快补偿轮询，关闭时降低频率。已收到的通知延后相应轮询；缺失超过两分钟的电量不再显示为当前值。
- 用户主动断开后不自动连接；睡眠停止控制会话，唤醒保留用户之前的断开意图。
- 模式和开关的界面值来自设备。可读设置写后再读；查找耳机这类无读接口只返回“请求已发送”。

## 界面与资源

使用 `NSStatusItem` 和 `NSPopover` 的系统开合行为，SwiftUI 管理可滚动的 360pt 面板。SDK 27 同名 State 宏在 CLT 中没有插件，代码用指向原生 `SwiftUI.State` 的类型别名选择标准属性包装器；没有改动 SDK。

型号资源是 GPL 上游 JSON（X4 使用独立 EncoDeck 补充表），保留完整未知字段及固件约束。支持的功能由型号、运行时能力位与已成功解析的响应共同约束。设备控制不依赖网络。用户主动检查更新时使用 Sparkle 的原生窗口与安装辅助服务，通过签名 feed 下载并验证发行包。

## 多品牌

- `BrandCatalog` 将原始配置转换为统一型号、降噪、EQ 和开关能力。最长型号名优先，避免 FreeBuds Pro 吞掉 Pro 2–5；vivo 项目代号只接受完整令牌。
- `BrandFrameCodec` 增量处理 GAIA、华为 Legacy/MBB、RCSP 和漫步者流；长度、CRC/校验和、完整 TLV 均检查。MBB 未解释的分片不解读为设置状态，且原表所有华为型号仍走 Legacy。
- `Command.*` 在新后端只作为已有 UI 的能力键。线上的命令由品牌模块产生；OPPO 原始 query 接口拒绝其他品牌。
- 华为多设备列表收集完整计数后再发布；超时保留原列表，不把半张列表当完整列表。只有能识别本机地址时才开放连接操作，并保护当前 Mac。
- 公开写操作必须通过型号和有效回读门控。无法回读的查找命令及 FreeBuds 3 旧开关仅返回“已发送”，不乐观勾选。vivo 双连开启状态没有确认的读接口，保留未知；列表管理在有真实响应时开放。
- 无盒的头戴式/颈挂/眼镜沿用同一电量区域，按原型号表显示单电池；三路耳机的现有布局不变。

## 启动与打包

先显示菜单栏入口，在后台读取型号目录，首次打开面板时才创建 SwiftUI 视图。型号 ID、名称和别名在加载时建立索引；后台设备查找复用同一份目录。登录项状态仅在进入设置时读取，空闲时不创建加载动画。蓝牙事件继续触发去抖后的查找，补偿查找在面板打开时每 8 秒、后台每 30 秒执行一次；手动刷新仍立即执行。

发行包仅包含应用、五份紧凑 JSON、无损压缩图标和许可。原始 vivo 表保留在 `docs/reference/`；诊断预览与硬件演练入口仅编入 debug 构建。蓝牙协议握手等待、请求超时和设备响应确认保持协议要求。
